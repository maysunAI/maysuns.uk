① 项目是什么

PJ50_personal_website（原 PJ44）是 Jason / maySunAI 的个人品牌网站，域名 maysuns.uk。

用一句话概括定位的演变：

2026-07-08 立项时 → 面向「找工作 + 吸引投资 + 加关注引流」三类受众的单页简历型网站。
2026-07-18 第一次大改版 → 从单文件单页站改造成多页静态站，定位从「求职简历」转向「产品门户 + 投资人/合作伙伴门面」。
2026-07-19 第二次改版 → 从「产品卡片堆砌」改成「讲故事型展示」（菜单分层 + Featured Story + 信任指标）。

当前站点包含：首页、About、Portfolio、10+个产品详情页、3个AI知识库页面（含15篇真实技术文章）、动态/更新日志、未来展望等约20+个HTML页面，纯 HTML+CSS+少量内联JS 实现，无框架、无构建步骤。

② 从0开始：最初的需求

项目起点是用户 2026-07-08 的原话（逐字保留）：

"maysuns.uk 是根目录，需要你更新内容。你全权处理。多个目的，
a.找工作， b，吸引投资，c。加关注，引流 等等，是不是一个目的一个文件夹？"

用户给予「全权处理」授权，可做实际内容/结构决策，无需逐条确认；但约定了两条边界：不得部署上线（部署步骤留给用户）、不得改动任何支付/API Key/密钥相关配置。

第一个关键决策：要不要"一个目的一个文件夹"？

结论：不采用。改为「单一个人品牌叙事 + 每个受众独立锚点区块」的结构。

理由：个人网站的核心资产是"这个人是否可信、是否讲得清楚一个连贯的故事"。如果把找工作/投资/引流拆成三个完全独立的页面，容易变成三套互相矛盾或重复的自我介绍，反而稀释可信度。但三类受众确实需要不同的"第一屏信息"和不同的行动号召——所以折中方案是：共享同一套背景故事（25年SE + 2023年起AI自学历程），再为三类受众各设一个独立区块（招聘方/投资人/关注者），首屏下方放快捷入口让访客一眼跳到自己关心的区块。

这个"共享身份 + 分受众区块"的思路，后来在多次改版中始终延续（例如首页仍保留 Featured Story，产品详情页各自独立但共享导航和视觉系统）。

③ 技术方案与取舍

方面选择为什么
框架无（纯 HTML + CSS + 少量内联JS）个人网站，页面数量有限，用框架增加构建步骤和维护成本，收益不明显
多语言不用 i18n 库，自建 data-i18n 属性 + assets/i18n.js 字典对象延续"单文件/零外部依赖"路线，避免引入构建步骤
Markdown渲染（知识库页）手写几十行小函数，不引入 marked.js 等CDN库全站"零外部依赖"约定——CDN被墙或挂了会导致功能整体失效；知识库文档语法简单，手写渲染器完全够用
托管Vultr 服务器 + nginx（2026-07-19从GitHub Pages迁移）跟其他 maysuns.uk 子站（shop/games/reader）同台，统一管理
DNSCloudflare域名 maysuns.uk 绑定，A记录直接指向服务器IP
HTTPSLet's Encrypt（certbot自动续期）免费、自动化程度高

GitHub仓库（github.com/maysunAI/maysuns.uk）仍保留作为版本历史/备份，但不再是实际托管源——每次改动都是"本地改 → git commit/push（存历史）→ scp上传到Vultr（真正生效）"两步分开的流程。

⑥ 部署流程

纯静态文件站点，部署是"本地改 → 存历史 → 上传生效"三步，没有构建/编译环节：

1. 本地改完文件
2. git add / commit / push（github.com/maysunAI/maysuns.uk，保留版本历史）
3. scp -i ~/.ssh/pj23_vultr_deploy -r <改动的文件> \
     root@167.179.106.32:/var/www/pj50-website/
4. 纯静态文件，nginx直接生效，不需要重启/重新构建任何东西

nginx配置：/etc/nginx/sites-enabled/maysuns.uk
证书：Let's Encrypt（certbot管理，自动续期，到期日2026-10-17）

缓存版本号（cache busting）

共享资源（site.css/i18n.js/main.js）的引用都带版本号参数，例如 assets/i18n.js?v=20260731b。每次真正改了这几个共享文件并重新部署时，把版本号改掉（通常用部署日期），浏览器会当成新地址重新下载，不再用旧缓存。这是2026-07-20修的一个真实bug："语言切不回来/页面显示老内容"排查后发现不是代码逻辑问题，是浏览器缓存了旧版 i18n.js。

本地预览规则

每次改完东西重新起本地预览服务器（python -m http.server）都要换一个新端口，避免浏览器缓存旧端口内容导致"确认的总是旧版本"。

验证方式

部署后用 curl 确认线上文件已更新 + 用 Playwright 直接打开真实域名截图核对内容，不能只在本地验证就算完成——2026-07-20曾发生过"本地改完但从未部署，用户看到的一直是老版本"的真实事故。

⑦ 关键设计决策（踩过的坑）

以下摘自项目 DESIGN.md，只记录"为什么这么设计"，不是操作步骤：

导航下拉菜单"要点两次"的bug

问题：下拉菜单跟触发文字之间留白（margin-top:12px），鼠标从文字移到菜单要穿过一段"真空地带"，穿过时 :hover 状态先丢失，菜单消失。
解法：改成零间距（margin-top:0），菜单卡片直接贴着导航文字下方，不依赖JS的标准解法。

sticky导航栏不生效

问题：顶部导航栏没有一直固定在页面顶部。
根因：position:sticky会被祖先元素上非visible的overflow值破坏——这是个常被忽略的CSS坑，sticky失效往往不是sticky本身的问题。html/body上原来有 overflow-x:hidden（为了防止内容撑破横向宽度加的），正是它破坏了sticky。
解法：删除 html/body上的overflow-x:hidden，只保留 max-width:100%；需要横向滚动的内容（如代码块）改成组件级自带 overflow-x:auto。

两个"看起来相似"的导航项，不能套用同一改法

Game Hall 和 Maysun Shop 一开始被同等对待，都想直接跳转到产品本身（不经过站内介绍页）。后来发现 Shop 以后会有多个销售渠道（Web商店/KDP/Google Play/Apple Store），不应该绑死跳到单一渠道，改回站内汇总页；Game Hall 只有一个真实产品，维持直跳。教训：看起来相似的两个功能点，实际情况不同时不能默认套用同一个改法。

查询参数命名坑：不能用 ?url=

给知识库文档查看器设计"通过链接参数加载远程md文件"功能时，参数名一度想叫 url，但 Vite 开发服务器把 ?url=当成自己内部"资源当URL导入"的保留写法，导致页面403打不开。改用 ?src=后正常——这也是为什么最终这个功能落地在 PJ26 而不是 PJ25（PJ25为了应用商店审核策略保持"无网络请求"，加载远程内容的功能不适合放在PJ25）。

⑨ 术语表

i18n（Internationalization 的缩写）
国际化/多语言支持。PJ50用 data-i18n 属性标记文本节点，配合 assets/i18n.js 里的三语字典对象实现切换，不引入外部i18n框架。

CDN（Content Delivery Network）
内容分发网络。PJ50故意不依赖任何CDN库（如marked.js），保持"纯本地文件、零外部网络依赖"，避免CDN被墙或宕机导致页面功能失效。

sticky positioning
CSS定位方式，元素滚动到指定位置后固定，常用于顶部导航栏。PJ50踩过的坑：祖先元素的overflow设置会让sticky失效。

cache busting
缓存清除技巧。给共享资源URL加版本号参数（如?v=20260720c），改动后修改版本号，强制浏览器重新下载而不是用旧缓存。

DNS（Domain Name System）
域名系统，把 maysuns.uk 这样的域名解析成服务器IP。PJ50用Cloudflare管理DNS，A记录直接指向Vultr服务器IP。

nginx
Web服务器软件，负责把域名请求映射到服务器上的静态文件目录并返回。PJ50的nginx配置在 /etc/nginx/sites-enabled/maysuns.uk。

Let's Encrypt
免费的HTTPS证书颁发机构，配合certbot工具自动续期。PJ50用它给maysuns.uk启用HTTPS。

anchor section（锚点区块）
页面内可以通过URL片段（如 #investors）直接跳转到的区块。PJ50最初的"三受众"设计用锚点区块区分招聘方/投资人/关注者，而不是拆成独立页面。
